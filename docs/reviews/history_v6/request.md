# M045 — History Generator v6 Phase A: Event-Driven Core Prototype

## 0. 작업 목표

Godot CRPG 프로젝트의 역사 생성기 v6를 위한 **독립적인 사건 기반 생성 코어**를 구현한다.

이번 작업은 v5의 리팩터링이나 v6 전체 구현이 아니다. 기존 v5의 역사 생성 알고리즘을 대체할 수 있는 새로운 아키텍처의 타당성을 검증하는 **Phase A 실험**이다.

핵심 철학:

> History is the accumulation of changes to the world state, not the completion of a predetermined narrative.

참고 아키텍처:

- Caves of Qud: 역사 상태와 사건 규칙의 조합
- Dwarf Fortress: 지속적인 상태 변화와 사건의 누적
- Storylet Architecture: 조건부 사건 선택과 상태 갱신
- Event Sourcing: 사건 기록으로부터 현재 상태 재구성

중요한 것은 이러한 시스템의 핵심 원리를 가져오는 것이지, 별도의 범용 시뮬레이션 프레임워크를 구축하는 것이 아니다.

**최우선 목표는 단순성, 조합 가능성, 확장성이다.**

## 2. Phase A의 아키텍처

다음의 간결한 실행 흐름을 구현한다.

```text
Canon + Seed
      │
      ▼
Initial World State
      │
      ▼
┌─────────────────────────────┐
│      History Engine         │
│                             │
│ 1. Enumerate Eligible Rules │
│ 2. Select Event Type        │
│ 3. Select Parameters        │
│ 4. Validate Effects         │
│ 5. Apply State Transition   │
│ 6. Record Historical Event  │
│                             │
└──────────────┬──────────────┘
               │
        Repeat / Advance Time
               │
               ▼
     Historical Event Log
               +
        Final World State
```

가능한 한 적은 수의 명확한 책임으로 구성한다.

필요한 핵심 개념:

### A. HistoryWorldState

특정 시점의 객관적인 역사적 세계 상태.

Phase A에서 필요한 최소 항목:

- 활동 중인 세력과 세력 계보
- 인구 집단의 출처와 소속
- 장소와 소유권
- 장소의 물리적 상태
- 세력 간 관계
- 유물 또는 중요 물건의 소유·위치·상태
- 현재 연도

모든 게임 시스템을 여기로 옮기지 않는다.

WorldState는 Phase A에서 사건을 생성하는 데 필요한 정보만 보유한다.

독립적인 상태의 복사, 조회, 검증과 결정적 직렬화가 가능해야 한다.

### B. HistoryEventRule

독립적으로 재사용할 수 있는 역사적 사건 규칙.

각 규칙은 다음을 정의한다.

- 고유한 규칙 ID
- 적용 가능한 상태와 참여자 조건
- 유효한 참여자 및 대상 조합
- 선택 가중치
- 사건 실행 시 발생하는 상태 변화
- 필요한 경우 원인 또는 선행 사건 참조

규칙 자체는 현재 상태를 직접 변경하지 않는다.

사건의 후보를 만들고 그 효과를 제안하는 역할만 한다.

### C. HistoryEventSelector

현재 상태에서 발생할 수 있는 규칙을 선택한다.

순서:

1. 조건을 만족하는 사건 유형을 수집한다.
2. 사건 유형별 가중치를 적용한다.
3. 사건 유형을 먼저 선택한다.
4. 해당 유형의 유효한 참여자와 매개변수를 별도로 선택한다.

**후보 매개변수의 개수가 사건 유형의 선택 확률을 의도치 않게 증가시켜서는 안 된다.**

v5에서 수정했던 split parameter multiplicity bias를 재도입하지 않는다.

동일한 조건, Seed, 콘텐츠 버전에서 동일한 사건이 생성되어야 한다.

### D. HistoryReducer

사건의 효과를 WorldState에 적용한다.

가능한 공통 연산 예시:

- CreateEntity
- RetireEntity
- TransferOwnership
- ChangeRelationship
- MovePopulation
- ChangeSiteCondition
- CreateArtifact
- MoveArtifact

이 목록은 설계 참고이며, 실제로 필요하지 않은 연산을 억지로 추가하지 않는다.

핵심 요구:

- 효과의 적용 전 조건을 검증한다.
- 잘못된 참조와 불가능한 상태 변경을 거부한다.
- 한 사건의 효과는 원자적으로 적용한다.
- 중간 실패 시 WorldState가 부분적으로 변경되어서는 안 된다.
- 검증 실패를 무시하고 진행하지 않는다.
- 같은 Event Log를 재생하면 동일한 최종 상태가 만들어진다.

### E. HistoricalEventLog

발생한 사건을 순서대로 보존한다.

최소 정보:

- Event ID
- Year
- Event Rule ID
- Participants
- Targets
- Effects
- 명시적으로 확인된 선행 사건 또는 원인 ID

중요:

시간상 먼저 발생했다는 이유만으로 인과관계를 만들어서는 안 된다.

원인을 모르는 사건은 원인 없이 기록할 수 있어야 한다.

또한 사건의 서술문은 객관적 상태와 분리한다. Phase A에서 풍부한 자연어 역사 생성은 필요하지 않다.

## 3. 최소 사건 규칙 구현

아키텍처를 검증할 수 있도록 다음 사건 유형을 구현한다.

기존 v5의 상세 시나리오를 복제하지 말고, 최소한의 범용 규칙으로 구현한다.

### 1. Faction Split — 세력 분열

조건:
- 활동 중인 세력이 존재한다.
- 분열 가능한 인구·제도적 조건을 만족한다.

효과:
- 기존 세력으로부터 새로운 세력이 형성된다.
- 정치적 계보가 기록된다.
- 인구의 출처와 분배가 보존된다.
- 필요하면 관계와 점유권이 변화한다.

기존 세력이 항상 소멸하거나 항상 살아남도록 강제하지 않는다.

### 2. Migration — 인구 이동

조건:
- 유효한 출발 집단과 도착 지역이 존재한다.

효과:
- 인구 집단의 위치나 소속이 변화한다.
- 출처 정보는 유지한다.
- 상황에 따라 기존 세력과의 관계에 영향을 준다.

단순한 세력 이름 변경이 아니라 실제 상태 변화여야 한다.

### 3. Site Reoccupation — 장소 재점유

조건:
- 현재 이용되지 않는 장소가 존재한다.
- 해당 장소를 점유할 수 있는 활동 중인 세력이 존재한다.

효과:
- 점유권 또는 사용 상태가 바뀐다.
- 이전 장소의 역사와 물리적 상태는 보존한다.

재점유만으로 파괴된 기술이 자동 복구되거나, 알려지지 않은 기술 지식이 생성되지 않도록 한다.

### 4. Relationship Change — 관계 변화

조건:
- 서로 다른 활동 중인 세력이 존재한다.

효과:
- 관계 상태가 변화한다.
- 이전 관계와 변화 내역이 사건으로 기록된다.

변화의 정당한 이유가 존재할 때만 인과관계를 명시한다.

### 5. Site Incident — 지역 사고

조건:
- 영향을 받을 수 있는 활동 중인 장소가 존재한다.

효과:
- 시설의 상태나 접근 가능성 등이 변경된다.
- 일부 물리적 결과가 장기간 남을 수 있다.

어떤 사고인지에 따라 결과가 달라질 수 있지만, 과도한 Scar 시스템을 구현하지 않는다.

### 6. Artifact Transfer / Loss — 중요 물건의 이동 또는 유실

조건:
- 소유자 또는 위치가 확인되는 물건이 존재한다.

효과:
- 소유권이나 보관 위치가 바뀐다.
- 이동 또는 유실 사건이 기록된다.
- 이전 이력은 유지된다.

향후 유물의 생애와 아이템 생성 시스템으로 확장할 수 있는지 확인한다.

### 사건 간 조합 검증

개별 사건이 작동하는 것만으로 충분하지 않다.

다음과 같은 연결이 자연스럽게 발생해야 한다.

- 세력 분열 → 관계 악화 → 장소 점유권 변화
- 인구 이동 → 장소 재점유 → 새로운 세력 관계
- 사고 → 장소 유기 → 후대 재점유
- 물건의 유실 → 후대 발견 또는 소유권 이전

모든 연결을 강제로 발생시키지 않는다.

**앞선 사건이 만들어낸 상태가 이후 사건의 조건을 변경하는지** 검증한다.

## 4. 역사 생성 루프

초기 세계에는 소수의 세력, 인구, 장소, 물건만 둔다.

현재 v5의 고정된 7개 topology family 또는 최종 세력 수 목표를 복제할 필요는 없다.

Phase A에서는 작은 세계를 대상으로 제한된 수의 사건을 순차적으로 생성한다.

### 필수 성질

1. 사건 발생 조건을 매 단계 재평가한다.
2. 사건의 적용 결과가 다음 사건 선택에 영향을 준다.
3. 불가능한 사건은 선택되지 않는다.
4. 사용 가능한 사건이 없는 경우 정상 종료하거나 시간을 진행한다.
5. 의미 없는 반복 사건이 무한정 발생하지 않는다.
6. 사건의 시간 순서는 항상 유효하다.
7. 명시적 선행 조건이 필요한 사건은 이를 만족해야 한다.
8. 특정 사건이 선택되지 않았다는 이유로 강제로 다른 사건을 끼워 넣지 않는다.

### 다양성 제어

시간에 따라 모든 세계가 비슷한 패턴으로 수렴하지 않도록 검토한다.

가능한 방법:

- 사건별 가중치
- 현재 상태에 따른 가중치 조정
- 최근 사건과의 반복 패널티
- 사건 유형별 cooldown
- 자원·장소·세력 조건의 변화

그러나 처음부터 모든 메커니즘을 구현하지 않는다.

필요한 최소 기능만 도입하고, 추가 복잡성이 정당한지 테스트로 확인한다.

### RNG 설계

Seed 기반 결정론적 생성을 유지한다.

가능하면 독립적인 RNG namespace를 사용해 다음을 분리한다.

- 사건 유형 선택
- 참여자 선택
- 사건 매개변수
- 상태와 무관한 표현 요소

같은 시드의 반복 실행은 동일해야 한다.

후속 사건 정의의 추가나 데이터 순서 변경이 무관한 결과까지 불필요하게 바꾸지 않도록 설계한다. 다만 상태 의존적 연쇄 변화는 정상적인 결과로 취급한다.

## 5. Canon과 역사적 진실

기존 CanonPolicy의 제약을 유지한다.

세 가지를 명확하게 구분한다.

1. Objective Fact: 실제로 발생한 사건과 효과
2. Historical Claim: 세력이 주장하는 해석
3. Unknown: 객관적으로 확인되지 않은 사실

Phase A의 코어는 Objective Fact만 생성한다.

역사적 주장과 문학적 서술은 구현 범위에 포함하지 않는다.

특히 다음 사항을 준수한다.

- 새로운 역사적 사건이 관리자 제국의 비밀을 임의로 확정하지 않는다.
- Preservator/Observer의 목적이나 의식을 추측해 사실로 기록하지 않는다.
- 사람이나 집단의 Origin을 기존 근거 없이 변경하지 않는다.
- 역사적 사건의 시간적 연관을 자동으로 인과관계로 해석하지 않는다.
- 기술의 보유, 관찰, 이해, 실제 작동 능력을 혼동하지 않는다.
- 행성 외부나 심층으로의 진출이 성공했다는 설정을 무단으로 생성하지 않는다.

Phase A에서는 이러한 소재의 구체적인 Project/Scar를 추가할 필요가 없다.

Canon 규칙의 적용 방법을 검토하고, 불가능한 변화가 거부되는 테스트를 포함하면 충분하다.

## 6. 데이터 모델과 확장성

향후 사건 종류가 늘어나더라도 엔진의 핵심 코드를 수정할 필요가 없도록 설계한다.

단, 과도한 추상화는 금지한다.

다음을 피한다.

- 범용 AI Agent Framework
- 범용 정치·경제 시뮬레이터
- 별도의 DSL 인터프리터
- 복잡한 이벤트 버스
- 불필요한 추상 팩토리 계층
- 사건마다 새로운 상속 계층
- 모든 게임 시스템을 역사 코어에 결합하는 구조
- 불필요한 전역 싱글턴
- 무제한 JSON Dictionary에 의존하는 불명확한 데이터 계약

Godot/GDScript의 특성을 고려해 단순한 RefCounted 클래스, 명시적인 자료형, 검증 가능한 데이터 정의를 우선한다.

공통 연산은 규격화하되, 각각의 사건이 필요한 고유한 검증 조건을 표현할 수 있어야 한다.

핵심 아키텍처의 규모를 가능한 한 작게 유지한다.

**새로운 역사 사건 추가 비용을 줄이는 것이 목표이며, 단순히 파일 개수를 줄이는 것은 목표가 아니다.**

## 7. 검증과 비교

### A. 단위 테스트

다음을 포함한다.

- 유효한 사건 후보 탐색
- 무효 후보 배제
- 사건 유형과 매개변수 선택 분리
- 상태 변화 적용
- 중간 오류 시 원자적 롤백
- 인구·세력 계보 보존
- 장소 소유권과 상태 정합성
- 물건의 소유·위치 일관성
- 시간적 정합성
- 잘못된 참조 거부
- Canon 위반 거부
- 동일 Seed 재생성
- Event Log를 이용한 최종 상태 재구성

### B. 생성 결과 테스트

초기에는 최소 100개의 Seed를 대상으로 상태와 사건 연결을 검증한다.

안정성이 확보되면 1,000개 이상의 Seed를 생성하여 다음 통계를 출력한다.

- 세계당 사건 수
- 사건 유형별 빈도
- 세력 수 분포
- 세력 형성·소멸·이동 빈도
- 장소 점유권 변경
- 유물 이동 이력
- 사건 간 인과적 연결 수
- 연속적으로 반복된 동일 유형의 사건
- 생성 중단 원인
- 실패와 불변조건 위반
- 동일 Seed replay 일치 여부

사건 유형이 다양하게 출력되었다는 것만으로 창발성이 검증되었다고 주장하지 않는다.

실제 상태 변화의 조합을 확인한다.

### C. 정성 검토

고정 Seed와 무작위 Seed를 모두 포함해 최소 10개의 역사를 사람이 읽기 좋은 형식으로 출력한다.

각 역사에는 다음을 보여준다.

- 초기 상태
- 사건의 연대기
- 사건별 변화
- 명시적 인과관계
- 최종 세계 상태

특히 다음을 검토한다.

- 유사한 사건이 반복되는가?
- 서로 다른 Seed에서 실제로 다른 변화가 발생하는가?
- 사건이 단순한 문장 변형에 그치지 않는가?
- 이전 사건의 결과가 후속 사건에 영향을 주는가?
- 결과가 세계관상 개연적인가?

관찰된 문제를 솔직하게 기록한다.

### D. 기존 테스트

전체 `tools/check_godot.sh`를 실행한다.

기존 v2/v3/v4/v5의 fixtures와 생성 결과가 변하지 않았는지 확인한다.

v6의 새로운 출력이 v5와 일치할 필요는 없다.

기존 버전의 동작만 보존하면 된다.

## 8. v5와 아키텍처 비교 보고서

구현 후 단순히 테스트 통과만 보고하지 말고, 기존 v5와 구조를 비교한다.

필수 비교 항목:

| 항목 | v5 | v6 Phase A |
|---|---|---|
| 핵심 생성 방식 | 기존 구현 분석 | 새로운 구조 |
| 생성 단계의 결합도 | 실제 코드 조사 | 실제 코드 조사 |
| 사건 정의 추가 방법 | 기존 구조 | 신규 구조 |
| 상태 변경 책임 | 기존 구조 | 신규 구조 |
| 결정론 보장 방법 | 기존 구조 | 신규 구조 |
| 기존 버전 의존성 | 실제 의존 관계 | 실제 의존 관계 |
| WorldState와 이벤트의 역할 | 기존 구조 | 신규 구조 |
| 예상 유지보수 비용 | 근거 포함 | 근거 포함 |

기존 v5는 완성도가 높은 시스템이고 v6는 최소 프로토타입이라는 점을 감안한다.

단순히 v6의 코드가 짧다는 이유로 더 우수하다고 판단하지 않는다.

**공정한 평가 기준은 동일한 종류의 사건을 추가하거나 수정할 때 필요한 변경 범위와 개념적 복잡성이다.**

추가로 다음 두 작업을 실제로 시험한다.

1. 기존 사건 하나의 발생 조건과 효과를 변경하기
2. 기존 코어를 수정하지 않고 새로운 소규모 사건 유형 하나를 추가하기

어떤 파일을 수정했고 어느 부분에서 결합도가 발생했는지 기록한다.

실험용 추가 사건은 테스트 전용으로 유지할 수 있다.

## 9. Phase A에서 구현하지 않을 것

다음은 명시적으로 범위에서 제외한다.

- 기존 283개 역사적 사건의 전면 이식
- 8개 Project와 15개 Scar의 이식
- 본격적인 역사적 인물 시뮬레이션
- 경제 시스템
- 완전한 세력 AI
- 역사적 Claim 생성
- Trace/Question/Investigation 재구현
- 역사적 유물의 실제 게임 아이템화
- 유적의 실제 월드맵 배치
- NPC 대화 시스템
- 전투·퀘스트 시스템 통합
- 기존 세이브 마이그레이션
- UI 제작
- v6의 기본 생성기 전환

이 기능들은 Phase B/C/D의 검토 대상이다.

Phase A에서는 **작은 사건 집합으로 유효하고 다양하며 누적적인 역사를 만들 수 있는가**만 검증한다.
