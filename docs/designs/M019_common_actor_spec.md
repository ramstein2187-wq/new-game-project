# M019 — 공통 Actor 구조 및 다수 NPC 지원

## 0. 작업 목표

현재 Godot 기반 CRPG 프로젝트의 플레이어·NPC·몬스터 관리 구조를 공통 Actor 모델로 리팩터링하고, 다수의 NPC가 독립적으로 행동하는 환경을 구현하라.

이번 작업은 단순히 Actor 클래스를 추가하는 것이 아니다.

현재 플레이어와 쥐의 상태가 별도 변수와 딕셔너리에 분산되어 있으며, 일부 시스템은 `player`와 `rat`라는 특정 ID에 의존한다.

이 구조를 개편하여 향후 인간형 NPC, 다양한 동물과 몬스터, 동료, 팩션, 장비, 상태 효과, 월드 영속성 등을 추가할 수 있는 기반을 마련한다.

다만 이번 마일스톤에서는 실제로 필요한 기능에 집중하고, 아직 구현하지 않을 미래 시스템을 위해 불필요한 추상화나 거대한 프레임워크를 만들지 않는다.

**핵심 목표는 기존 게임 규칙을 유지하면서, 개체 수와 종류를 확장할 수 있도록 데이터 소유권과 행동 처리 구조를 통합하는 것이다.**

작업 시작 전에 반드시 실제 프로젝트 코드와 문서를 확인하라. 아래에 기술된 현재 상태는 작업 지침을 제공하기 위한 것이며, 실제 코드와 차이가 있다면 최신 코드 및 검증된 설계 문서를 기준으로 판단하라.

설계가 불명확한 부분은 현재 구현된 규칙을 보존하는 최소한의 방식으로 결정하고, 결정 이유를 마일스톤 문서에 기록하라.

## 3. 목표 아키텍처

권장하는 기본 구조는 다음과 같다.

```text
Game / World
│
├── ActorRegistry
│   ├── Actor: player
│   ├── Actor: rat_001
│   ├── Actor: rat_002
│   └── Actor: rat_003
│
├── TimeScheduler
│
├── Common Action System
│
├── Tactical AI
│
├── Combat Rules
│
└── Combat Event Log
```

개별 Actor는 다음 세 요소를 바탕으로 구성한다.

```text
ActorDefinition
       │
       ▼
     Actor
       │
       ▼
ActorController / AI Policy
```

여기서 ActorDefinition은 정적 정의, Actor는 개체별 상태, Controller 또는 AI Policy는 행동 결정 주체를 나타낸다.

세 요소의 책임을 분리하되, 현재 구현 범위에서 실제로 필요하지 않은 추상 클래스나 인터페이스를 불필요하게 추가하지 마라.

기존 코드와 더 잘 맞는 구조가 있다면 일부 명칭과 세부 구현을 조정할 수 있다.

단, 공통 데이터 소유권과 플레이어·NPC의 행동 결정 분리라는 핵심 원칙은 유지해야 한다.

## 4. ActorDefinition 구현

공통 Actor 정의를 위한 `ActorDefinition`을 구현하라.

권장 형태:

```gdscript
class_name ActorDefinition
extends Resource
```

이 클래스는 같은 종류의 액터가 공유할 수 있는 기본 데이터를 보유한다.

포함할 데이터:

* 종족 또는 개체 유형 식별자
* 기본 표시 이름
* 기존 CombatSpecies 참조
* 기본 최대 HP
* 기본 능력치 또는 능력치 초기화 설정
* 기본 행동 비용
* 기본 AI 정책 또는 행동 유형 식별자

가능하다면 기존 `CombatSpecies` 및 `BodyTemplate` 구조를 재사용하라.

정적 정의를 위해 중복된 종족·신체 시스템을 새로 만들지 마라.

### 4.1. 정적 정의와 개체별 상태 분리

ActorDefinition에는 다음과 같은 개체별 가변 상태를 넣지 않는다.

* 현재 HP
* 현재 위치
* 현재 신체 손상
* 현재 공포
* 현재 목표
* 개체별 행동 시간

서로 다른 Actor 인스턴스가 동일한 ActorDefinition을 참조하더라도, 한 개체의 부상이나 상태 변경이 다른 개체에 영향을 주어서는 안 된다.

현재는 코드 기반 팩터리로 인간과 쥐 정의를 생성해도 된다.

다량의 외부 Resource 파일을 새로 만드는 작업은 실제 필요성이 확인될 때 진행하라.

### 4.2. 초기 정의

우선 다음 두 종류를 지원하라.

`human_default`

기존 플레이어의 능력치, 신체, HP 및 행동 비용을 유지한다.

`rat_common`

기존 쥐의 능력치, 신체, HP 및 행동 비용을 유지한다.

이 단계에서는 전투 밸런스를 변경하지 않는다.

## 5. Actor 구현

개별 개체를 나타내는 공통 Actor 클래스를 구현하라.

권장 파일:

`time_cost/actors/actor.gd`

권장 형태:

```gdscript
class_name Actor
extends RefCounted
```

Actor가 보유해야 할 기본 정보는 다음과 같다.

### 5.1. 정체성

* `id: StringName`
* `definition: ActorDefinition`
* `display_name: String`

각 Actor는 고유한 ID를 가져야 한다.

플레이어는 기존 시스템과의 호환성을 위해 우선 `&"player"`를 유지한다.

여러 쥐는 `&"rat_001"`, `&"rat_002"`처럼 구분한다.

기존 단일 쥐 테스트와의 호환성이 필요하다면 초기 쥐에 `&"rat"`를 유지해도 된다.

단, 특정 ID의 쥐만 정상적으로 작동하는 구조를 남기지 마라.

고유 ID를 종족 식별자 대신 사용하지 마라.

### 5.2. 공간 상태

* 현재 위치
* 바라보는 방향
* 필요하다면 현재 지역 식별자

개체별 위치는 Actor가 소유한다.

기존 Game에 동일한 위치 데이터를 별도 가변 변수로 중복 저장하지 마라.

현재 지역 식별자는 미래 월드 영속성을 위한 확장 지점이며, 실제 지역 이동 및 저장 기능은 이번 범위에 포함하지 않는다.

### 5.3. 전투 상태

* 현재 HP
* 최대 HP
* AbilityScores
* BodyInstance

기존 전투 규칙을 유지하라.

각 Actor의 AbilityScores 및 BodyInstance는 다른 개체와 독립적이어야 한다.

동일한 종족 정의를 참조하는 두 쥐라도 한쪽의 능력치 변경이나 신체 손상이 다른 쥐에게 영향을 주면 안 된다.

### 5.4. 행동 상태

개체별 기본 행동 비용을 조회할 수 있어야 한다.

예를 들어 다음 행동을 구분할 수 있다.

```text
move_cardinal
move_diagonal
attack
interact
wait
```

기존 코드와의 호환성을 고려하여 구체적인 데이터 구조를 결정하라.

행동 비용은 Actor의 정적·기본 설정으로부터 조회하되, 실제 비용 계산은 해당 Action이 담당한다.

### 5.5. AI 및 개체별 성향

최소한 다음 정보를 개체별로 관리할 수 있어야 한다.

* AI 정책 식별자
* 기본 공격성
* 공포 관련 개체별 상태

현재 쥐의 공격성 및 공포 계산 방식을 유지하면서 각각의 쥐가 독립적인 성향과 부상 상태에 따라 행동하도록 하라.

현재 HP 감소에 따른 공포 계산과 별도 공포 보정값의 관계를 유지한다.

단순한 성향 데이터 때문에 새로운 범용 감정·성격 엔진을 만들지 마라.

### 5.6. Actor의 책임 제한

Actor는 자신의 상태를 보유하고 필요한 조회 기능을 제공한다.

다음 기능은 Actor의 책임이 아니다.

* 전체 게임 시간 관리
* 타 개체의 행동 순서 관리
* 전체 맵의 충돌 검사
* 전투 규칙 전체 계산
* 행동 선택 알고리즘 전체
* 모든 개체의 생성·제거
* 게임 UI 렌더링

Actor를 거대한 게임 매니저로 만들지 마라.

## 6. ActorRegistry 구현

Actor 인스턴스를 중앙에서 관리할 `ActorRegistry`를 구현하라.

권장 파일:

`time_cost/actors/actor_registry.gd`

핵심 역할:

* Actor 등록
* ID로 Actor 조회
* Actor 존재 여부 확인
* Actor 제거
* 특정 위치에 존재하는 Actor 조회
* 활성 Actor 순회

기본 API 예시:

```gdscript
register_actor(actor)
get_actor(actor_id)
has_actor(actor_id)
remove_actor(actor_id)
get_actor_at(position)
get_actors()
```

함수명은 기존 프로젝트 스타일에 맞게 조정할 수 있다.

### 6.1. 데이터 소유권

Registry는 현재 게임에 소속된 Actor 인스턴스를 관리한다.

TimeScheduler는 해당 Actor의 행동 시간과 순서를 관리한다.

두 시스템의 책임을 혼합하지 마라.

ActorRegistry에 `ready_time`을 중복 저장하거나 Actor 자체가 스케줄러의 시간 데이터를 독립적으로 관리하도록 만들지 않는다.

### 6.2. 중복 ID 및 위치 충돌

중복 ID 등록은 실패해야 한다.

동일한 위치에 둘 이상의 살아 있는 Actor가 배치되지 않도록 하라.

단, 향후 여러 개체가 같은 위치에 존재할 수 있는 특수 기능까지 지금 구현할 필요는 없다.

현재는 한 타일에 살아 있는 Actor 한 개체만 존재할 수 있는 규칙을 적용한다.

### 6.3. 개체 제거와 사망

개체 사망과 데이터 삭제를 분리하라.

현재 규칙에 따라 HP가 0이 된 개체는 더 이상 행동할 수 없어야 한다.

사망한 NPC는 TimeScheduler에서 등록 해제되어야 한다.

그러나 사망 즉시 Actor의 모든 데이터를 무조건 삭제하도록 강제하지는 마라.

향후 시체, 전리품, 월드 영속성에서 활용할 수 있도록 개체 상태를 보존하거나 제거할 수 있는 구조를 마련하라.

이번 마일스톤에서 시체·전리품 시스템 자체를 구현하지는 않는다.

플레이어가 사망한 경우 기존 게임 종료 규칙을 유지한다.

## 7. 기존 TimeCostGame 리팩터링

이번 작업의 핵심 단계다.

현재 `TimeCostGame`은 플레이어와 쥐를 개별 변수로 관리한다.

이를 공통 ActorRegistry 기반으로 전환하라.

### 7.1. 실제 데이터 소유권 변경

기존의 `player_position`, `rat_position`, `player_hp`, `rat_hp` 등은 Actor의 개별 상태로 이전한다.

게임이 위치나 HP를 필요로 할 때 ActorRegistry를 통해 해당 개체를 조회하게 하라.

다음과 같은 공통 API를 유지하거나 제공하라.

```gdscript
get_actor(actor_id)

actor_is_alive(actor_id)

get_actor_position(actor_id)

set_actor_position(actor_id, position)

damage_actor(actor_id, damage)

movement_efficiency(actor_id)

can_attack(actor_id)
```

기존 함수의 의미와 호출 계약을 가능한 한 보존하라.

특정 ID에 대한 분기문을 추가하는 방식으로 다수 NPC를 구현하지 마라.

### 7.2. 기존 테스트 호환성

현재 테스트와 UI가 기존 필드에 직접 접근할 수 있다.

가능하면 일시적인 호환 접근자를 제공하거나, 관련 호출부를 안전하게 이전하라.

예를 들어 기존 `game.player_hp`가 남아 있어야 한다면 Actor의 HP를 반환하고 수정하는 접근자로 구현할 수 있다.

이때 Actor와 Game에 서로 다른 HP 값이 존재해서는 안 된다.

`abilities`, `species`, `bodies` 딕셔너리도 실제 Actor 데이터와 동기화 문제가 발생하지 않도록 처리하라.

기존 테스트가 해당 딕셔너리 내부를 직접 수정하는 경우를 확인하고, 데이터의 실제 소유권이 Actor에 있도록 이전 전략을 수립하라.

호환성을 이유로 영구적인 이중 상태를 만들지 마라.

### 7.3. Game의 역할

Game은 다음 역할을 담당한다.

* ActorRegistry 관리
* TimeScheduler와 ActorRegistry의 연결
* 공통 Action 실행 조정
* 게임 규칙과 충돌 검사
* 전투 및 게임 종료 처리
* 이벤트 기록

개별 액터의 내부 상태와 전체 게임 상태를 명확히 구분하라.

## 8. 기존 TimeScheduler 유지 및 확장

현재 TimeScheduler는 ID별 행동 시간을 관리한다.

이번 작업에서는 해당 구조를 유지하라.

중요한 기존 규칙:

* 액터마다 독립적인 다음 행동 시간이 존재한다.
* 행동 완료 후 해당 액터의 다음 행동 시간을 비용만큼 증가시킨다.
* 플레이어와 NPC의 행동 가능 시간이 같다면 플레이어가 우선한다.
* NPC 사이의 동시간 처리는 기존 등록 순서 규칙을 유지한다.
* 행동 시간이 진행되는 방식과 기존 정수 시간 단위를 바꾸지 않는다.

여러 NPC가 존재할 때 스케줄러가 특정 `rat` ID에 의존하지 않고 다음 행동할 개체를 선택하도록 Game 측 처리 구조를 수정하라.

NPC 한 개체의 행동이 끝난 뒤 다른 개체가 행동해야 하는 경우도 정상 처리되어야 한다.

### 8.1. 행동 실패 처리

유효하지 않은 행동은 기존 규칙에 따라 시간을 소비하지 않으며 전투 이벤트를 생성하지 않는다.

다만 스케줄러에서 이미 행동 차례를 받은 NPC가 유효한 행동을 선택하지 못했을 때, 동일한 NPC를 무한히 반복 호출하는 상황이 발생해서는 안 된다.

AI는 실행 가능한 대기 행동을 포함한 유효한 후보를 반환하도록 설계하라.

예기치 않은 행동 실패가 발생하면 원인을 식별할 수 있도록 처리하고, 게임이 무한 루프에 빠지지 않도록 하라.

실패한 행동에 임의의 시간 비용을 부과해서 문제를 숨기지 마라.

### 8.2. 등록 및 제거 일관성

ActorRegistry와 TimeScheduler 사이에 등록 상태 불일치가 발생하지 않도록 하라.

개체 생성·등록·사망·제거 시 두 시스템의 관계를 명확히 관리하라.

예를 들어 등록에 실패한 개체가 살아 있는 게임 액터로 남아 있거나, 사망한 NPC가 다음 행동자로 계속 선택되어서는 안 된다.

## 9. 공통 Action 시스템 연결

기존 Action 클래스를 유지하면서 개체별 데이터 조회 방식을 통합하라.

### 9.1. MoveAction

개체별 기본 이동 비용을 조회하도록 수정하라.

기존 이동 비용:

| 개체   | 직선 이동 | 대각선 이동 |
| ---- | ----: | -----: |
| 플레이어 |  1000 |   1400 |
| 쥐    |   750 |   1050 |

대각선 이동 비용은 직선의 1.4배다.

기존 M017의 신체 부상에 따른 이동 효율 계산도 유지한다.

현재 적용되는 계산식:

```text
최종 이동 비용 =
ceil(기본 이동 비용 / 신체 이동 효율)
```

이동 효율이 0 이하라면 이동할 수 없어야 한다.

이번 작업에서 새로운 속도 능력치나 별도의 시간 정규화 시스템을 추가하지 않는다.

### 9.2. AttackAction

공격자의 ID와 대상의 ID를 사용하여 해당 Actor를 조회하라.

다음 정보를 특정 플레이어·쥐 변수에 의존하지 않고 조회할 수 있어야 한다.

* 공격자의 능력치
* 공격자의 종족 및 공격 유형
* 공격자의 신체 상태
* 공격 대상의 능력치
* 공격 대상의 신체 상태
* 대상의 현재 HP

기존 D20 명중, 신체 부위 피격, 방어구 관통 및 피해 계산을 유지하라.

개체별 기본 공격 비용을 적용하라.

### 9.3. InteractAction

기존 문 상호작용 기능을 보존하라.

현재 문과의 상호작용에 특정 플레이어·쥐 위치를 직접 참조하는 부분이 있다면 공통 점유 검사로 전환하라.

이번 작업에서 M002의 범용 상호작용 오브젝트 시스템까지 구현하지 마라.

### 9.4. WaitAction

모든 Actor가 대기 행동을 정상적으로 실행할 수 있어야 한다.

기존 대기 행동 비용 및 시간 처리 규칙을 유지하라.

### 9.5. 공격 가능 대상 판단

플레이어가 이동하려는 타일에 살아 있는 NPC가 있다면 해당 NPC를 대상으로 기존의 이동 입력 기반 근접 공격을 수행할 수 있어야 한다.

여러 NPC가 있어도 특정 쥐를 하드코딩하지 마라.

현재 프로토타입에서는 플레이어와 등록된 적대 NPC 사이의 전투를 가정해도 된다.

이번 작업에 팩션, 우호 대상 공격 제한, 동료 오인 공격 등의 완전한 적대 관계 시스템을 추가하지 않는다.

## 10. 다수 NPC를 위한 전술 AI 개편

기존 `TacticalPlanner`와 `RatTactics`를 재사용하라.

목표는 현재 쥐 한 마리만 지원하는 AI 정책을 임의의 쥐 개체에 적용할 수 있도록 만드는 것이다.

### 10.1. 개체별 판단

AI의 행동 선택 함수는 최소한 다음 정보를 활용할 수 있어야 한다.

```text
game
actor_id
target_id
```

필요하다면 현재 Actor 및 대상 Actor를 조회한 뒤 전달하는 구조를 사용해도 된다.

AI는 해당 개체의 다음 정보를 읽어야 한다.

* 위치
* HP 및 최대 HP
* 신체 손상
* 이동 기능
* 공격 기능
* 공격성
* 공포 관련 상태

다른 쥐의 상태를 자신의 상태로 잘못 참조해서는 안 된다.

### 10.2. 행동 후보

기존 AI의 다음 행동을 유지하라.

* 대상에게 접근
* 대상 공격
* 공포에 따른 후퇴
* 이동 불능 또는 행동 불가 시 대기
* 필요한 경우 기존 문 상호작용

기존 `TacticalChoice` 및 `TacticalPlanner` 기반의 후보 평가 구조를 유지한다.

기존 점수 체계나 공포 임계값을 임의로 변경하지 마라.

### 10.3. 개체별 독립성

예를 들어 다음과 같은 상황이 정상적으로 작동해야 한다.

```text
rat_001
HP: 30 / 30
Aggression: 80
Fear bonus: 0

rat_002
HP: 10 / 30
Aggression: 30
Fear bonus: 20

rat_003
HP: 30 / 30
Aggression: 50
Fear bonus: 0
```

각 개체는 자신의 상태에 따라 행동을 선택한다.

한 쥐가 부상당하거나 사망해도 다른 쥐의 신체·HP·AI 성향은 직접적인 영향을 받지 않아야 한다.

다른 쥐가 사망한 것을 목격했을 때 공포가 증가하는 등의 집단 AI는 이번 범위에 포함하지 않는다.

### 10.4. 경로 탐색 및 충돌

여러 NPC가 동일한 경로를 이용할 수 있는 상황을 고려하라.

기존 M018의 8방향 이동과 대각선 모서리 통과 제한을 유지해야 한다.

NPC는 다른 살아 있는 NPC의 타일을 점유할 수 없다.

이미 점유된 타일 때문에 이동이 막힌다면 유효한 다른 행동을 선택할 수 있어야 한다.

기존의 경로 탐색 방식을 무리하게 완전히 교체할 필요는 없다.

다만 기존 경로 탐색이 특정 쥐의 위치만 참조하거나, 다른 NPC를 장애물로 처리하지 못해 행동 실패를 반복한다면 필요한 범위에서 수정하라.

NPC들이 좁은 통로에 모여 있을 때도 무한 루프나 불가능한 이동 시도를 반복해서는 안 된다.

완전한 다중 에이전트 경로 계획이나 고급 협동 이동 시스템은 이번 범위에 포함하지 않는다.

### 10.5. 행동 이유 보존

기존 AI의 다음 정보가 유지되어야 한다.

* 행동 목표
* 행동 점수
* 점수 산정에 사용된 주요 요인
* 선택 이유 코드
* 플레이어가 관찰할 수 있는 행동 신호

특히 후퇴 행동에 대한 기존 로그와 개발자용 판단 추적 기능을 보존하라.

여러 NPC가 존재하더라도 어떤 개체가 어떤 이유로 행동했는지 구분할 수 있어야 한다.

## 11. 전투 로그 및 개체 식별

기존 `CombatEvent`와 `CombatEventLog` 구조를 유지하라.

모든 행동 이벤트는 실제 행동한 Actor의 ID를 사용해야 한다.

공격 이벤트는 올바른 대상 Actor의 ID를 기록해야 한다.

동일한 종족의 NPC가 여러 마리 등장할 때에도 전투 로그에서 개체를 구분할 수 있어야 한다.

예를 들어 다음과 같은 상황을 구분할 수 있어야 한다.

```text
rat_001 approaches the player.
rat_002 retreats.
rat_003 attacks the player.
```

위 문장은 예시이며, 반드시 동일한 영어 문장을 사용할 필요는 없다.

기존의 플레이어용 로그와 개발자용 상세 로그를 모두 고려하라.

현재 전투 로그 포매터의 `The rat`과 같은 하드코딩된 표현을 점검하고, 여러 NPC가 등장해도 의미를 이해할 수 있도록 필요한 범위에서 수정하라.

다만 전체 로그 시스템을 새로 설계하거나 언어 현지화 시스템을 추가할 필요는 없다.

로그 출력 시 내부 AI 점수나 비공개 판단 정보를 플레이어에게 무조건 노출하지 마라.

기존의 관찰 가능한 행동과 개발자용 디버그 정보 구분을 유지한다.

## 12. 실제 플레이 환경에 다수 NPC 구현

공통 Actor 구조가 데이터 계층에서만 작동하는 것으로 작업을 끝내지 마라.

실제 게임 화면에서도 여러 NPC가 등장하고 독립적으로 행동하는 것을 확인할 수 있어야 한다.

현재 기본 플레이 환경은 절차 생성 맵 전투 프로토타입이다.

관련 파일:

* `time_cost/generated_map_combat_game.gd`
* `time_cost/generated_map_combat_playground.gd`
* `time_cost/time_cost_test_room.gd`

### 12.1. 다수 NPC 생성

일반적인 플레이 환경에서 플레이어 1명과 쥐 3마리를 생성할 수 있도록 하라.

각 쥐는 독립된 Actor 인스턴스여야 한다.

각 개체는 다음 데이터를 독립적으로 가져야 한다.

* 고유 ID
* 위치
* HP
* 능력치
* 신체 상태
* AI 성향
* 행동 시간

### 12.2. 절차 생성 맵 배치

절차 생성 맵에서는 생성된 지형 중 유효한 위치에 NPC를 배치하라.

기존 플레이어 시작 위치 및 맵 생성 규칙을 유지한다.

배치 시 다음 조건을 충족해야 한다.

* 벽이나 통과 불가능한 지형에 생성되지 않을 것
* 다른 액터와 동일한 타일에 생성되지 않을 것
* 플레이어가 접근할 수 있는 영역에 생성할 것
* 일반적인 맵에서 적어도 3마리의 쥐를 생성할 수 있을 것
* 동일한 시드와 동일한 설정으로 재생성할 때 배치 결과가 재현 가능할 것

현재 월드 생성용 RNG와 전투 RNG는 분리되어 있다.

NPC 배치 때문에 기존 전투 결과의 RNG 소비 순서가 불필요하게 달라지지 않도록 하라.

가능하다면 별도의 결정적 배치 규칙 또는 독립적인 배치 RNG를 사용하라.

기존 절차 생성 알고리즘 자체를 변경하지 마라.

작은 테스트 맵 등에서 충분한 배치 공간이 없을 수 있으므로, 그 경우를 명시적으로 처리하고 기존 유효한 맵 구성이 불필요하게 실패하지 않도록 하라.

### 12.3. 테스트 룸

기존 고정 테스트 룸도 정상적으로 작동해야 한다.

다수 NPC 검증을 위해 고정 테스트 룸에 별도 배치 모드나 테스트 시나리오를 추가할 수 있다.

그러나 기본 테스트 룸의 기존 검증을 깨뜨리지 마라.

### 12.4. 화면 및 UI

플레이어와 다수 NPC를 각각 렌더링하라.

기존 단일 쥐 렌더링 분기문을 공통 ActorRegistry 기반 순회 방식으로 변경하는 것을 권장한다.

적어도 다음 정보가 확인 가능해야 한다.

* 플레이어의 위치와 HP
* 각 쥐의 위치
* 각 쥐의 생존 여부
* 다수 NPC의 행동 결과
* 기존 전투 로그 및 디버그 로그

기존 신체 및 능력치 실험 UI가 정상적으로 작동해야 한다.

적 개체를 선택하는 새로운 복잡한 UI까지 만들 필요는 없다.

화면 크기와 기존 레이아웃을 고려하여 단순하고 읽기 쉬운 표현을 사용하라.

## 13. 기존 게임 규칙 보존

이번 작업은 구조 개편이다.

기존 마일스톤에서 확정한 게임 규칙을 변경하지 마라.

### 13.1. 시간 및 이동

* 기존 정수 기반 행동 시간 유지
* 플레이어 우선 동시간 처리 유지
* NPC 등록 순서 기반 동시간 처리 유지
* 직선·대각선 이동 비용 유지
* 기존 신체 손상에 따른 이동 비용 증가 유지
* 대각선 모서리 통과 제한 유지

### 13.2. 전투

* 기존 D20 명중 판정 유지
* 기존 명중률 관련 능력치 적용 유지
* 기존 부위별 피격 및 내구도 유지
* 기존 방어구 관통 계산 유지
* 기존 부위 기능 저하 유지
* 기존 공격 비용 유지
* 기존 HP 및 신체 손상 관계 유지

특히 기존 M017에서는 전체 HP가 0이 되었을 때 사망하고, 특정 신체 부위의 내구도가 0이 되더라도 전체 HP와 별개로 처리된다.

이를 변경하지 마라.

### 13.3. RNG

기존 시드 기반 전투의 재현성을 유지하라.

동일한 초기 상태, 동일한 시드, 동일한 행동 순서에서 동일한 결과를 얻을 수 있어야 한다.

다수 NPC 구현으로 인해 새롭게 추가된 행동 자체가 전투 RNG를 소비하는 것은 자연스럽지만, 구조 개편만으로 동일한 단일 NPC 전투 시나리오의 결과가 변경되어서는 안 된다.

### 13.4. 기능 범위 제한

다음 기능은 이번 마일스톤에서 구현하지 않는다.

* 범용 인벤토리 및 장비 시스템
* 새로운 방어구·무기 밸런스
* 팩션 및 외교 시스템
* 퀘스트 시스템
* 동료 명령 시스템
* 플레이어의 다른 신체로의 이동이나 빙의
* 새로운 상태 효과 엔진
* 새로운 속도 능력치
* 월드 저장·불러오기 및 지역 간 NPC 이동
* 대규모 NPC 시뮬레이션 최적화
* 고급 집단 전술 AI
* 새로운 턴제 또는 AP 시스템

향후 확장이 가능한 구조를 확보하는 것으로 충분하다.

## 14. 자동 테스트 및 완료 조건

작업이 끝났다고 판단하기 전에 기존 테스트와 신규 테스트를 모두 검증하라.

가능하면 새로운 Actor 전용 테스트를 작성하라.

권장 테스트 파일:

```text
tests/test_common_actor.gd
tests/test_multiple_npcs.gd
```

기존 테스트 파일 구조에 맞게 명칭은 조정할 수 있다.

### 14.1. Actor 생성 및 독립성

검증 조건:

* 플레이어와 쥐가 모두 Actor로 생성된다.
* 서로 다른 Actor가 동일한 종족 정의를 참조할 수 있다.
* 각 Actor의 HP는 독립적이다.
* 각 Actor의 AbilityScores는 독립적이다.
* 각 Actor의 BodyInstance는 독립적이다.
* 한 쥐의 신체 부상이 다른 쥐에게 전파되지 않는다.
* 한 쥐의 AI 상태 변경이 다른 쥐에게 전파되지 않는다.
* 초기화 시 기존 데이터가 올바르게 복원된다.

### 14.2. Registry

검증 조건:

* 고유 ID로 Actor를 등록하고 조회할 수 있다.
* 중복 ID 등록이 거부된다.
* 여러 Actor를 독립적으로 관리할 수 있다.
* 현재 위치로 액터를 조회할 수 있다.
* 사망한 개체와 살아 있는 개체를 구분할 수 있다.
* 제거한 개체가 잘못된 상태로 스케줄러에 남지 않는다.

### 14.3. 이동 및 충돌

검증 조건:

* 각 Actor가 독립적으로 이동한다.
* 서로 다른 살아 있는 Actor가 동일한 타일을 점유할 수 없다.
* 벽과 기존 지형 충돌 규칙이 유지된다.
* 대각선 이동 규칙이 유지된다.
* 대각선 이동의 기본 비용은 직선의 1.4배다.
* 다리 부상에 따른 이동 비용 증가가 개체별로 적용된다.
* 이동 불능 개체의 이동 행동은 거부된다.

### 14.4. 행동 시간

검증 조건:

* 여러 NPC가 개별 행동 시간을 가진다.
* NPC 한 개체의 행동이 다른 NPC의 행동 시간을 직접 변경하지 않는다.
* 시간이 같은 경우 기존 우선순위 규칙을 따른다.
* 유효한 행동은 비용을 정확히 한 번 소비한다.
* 무효 행동은 시간과 전투 이벤트를 소비하지 않는다.
* 사망한 NPC는 더 이상 행동하지 않는다.
* 실행 가능한 행동이 없거나 경로가 막혔을 때 무한 루프가 발생하지 않는다.

### 14.5. 전투

검증 조건:

* 플레이어가 서로 다른 NPC를 각각 공격할 수 있다.
* 서로 다른 NPC가 플레이어를 각각 공격할 수 있다.
* 대상 Actor의 실제 신체 및 HP에 피해가 적용된다.
* 한 NPC의 사망이 다른 NPC의 HP나 신체 상태를 변경하지 않는다.
* 기존 명중 및 방어구 관통 규칙이 유지된다.
* 전투 이벤트의 공격자·대상 ID가 정확하다.

### 14.6. AI

검증 조건:

* 여러 쥐가 각자의 행동을 독립적으로 선택한다.
* HP와 공포 상태에 따라 서로 다른 행동을 선택할 수 있다.
* 이동 불능 쥐는 불가능한 이동을 반복하지 않는다.
* NPC 간 충돌이 정상 처리된다.
* 후퇴 행동의 이유와 관찰 가능한 신호가 유지된다.
* 행동 선택 및 이벤트 기록의 결정적 재현성이 유지된다.

### 14.7. 절차 생성 맵

검증 조건:

* 일반적인 맵에서 플레이어와 쥐 3마리를 생성할 수 있다.
* 서로 다른 위치에 배치된다.
* 유효한 지형에 배치된다.
* 플레이어가 접근할 수 있는 위치에 배치된다.
* 동일한 시드에서 초기 배치가 재현된다.
* 맵 재생성 시 이전 게임의 Actor가 남지 않는다.
* 기존 소형 맵 테스트 및 실패한 configure 처리 규칙을 보존한다.

### 14.8. 기존 테스트 회귀 검증

기존 M011~M018 관련 테스트를 실행하라.

특히 다음 영역의 회귀 여부를 확인하라.

```text
TimeScheduler
Common Action System
Tactical AI
Generated Map Combat
Combat Body
Eight-way Combat
Combat Log
```

기존 단일 쥐 테스트가 구조 개편으로 인해 실패한다면 새로운 구조에 맞게 테스트를 이전하되, 검증하려는 기존 게임 규칙을 유지하라.

기존 테스트를 삭제하거나 의미 없는 성공 조건으로 변경하지 마라.

`bash tools/check_godot.sh`를 실행할 수 있다면 실행하라.

환경상 실행하지 못한 검증이 있다면 그 사실을 명확히 보고하라.

## 15. 구현 순서

작업은 다음 네 단계로 진행하라.

### Phase A — Actor 기반 구축

1. ActorDefinition 구현.
2. Actor 구현.
3. ActorRegistry 구현.
4. 기존 플레이어와 쥐를 Actor 인스턴스로 생성.
5. 신체·능력치·HP 데이터의 독립성 테스트.

이 단계에서는 기존 전투 및 시간 규칙을 변경하지 않는다.

### Phase B — 기존 시스템의 공통 Actor 전환

1. TimeCostGame의 데이터 소유권을 Actor로 이전.
2. 기존 공통 Action 시스템 연결.
3. TimeScheduler와 ActorRegistry 연결.
4. 전투 및 신체 데이터 조회 전환.
5. 기존 UI·테스트 호환성 확보.

이 단계가 끝나면 기존 플레이어 1명과 쥐 1마리의 게임 동작이 구조 개편 전과 동일해야 한다.

### Phase C — 다수 NPC 지원

1. 여러 NPC 생성 및 등록.
2. 공통 위치·충돌 검사.
3. NPC별 행동 시간 처리.
4. 기존 RatTactics의 개체별 상태 및 대상 참조 전환.
5. 다수 NPC의 공격·이동·후퇴·대기·사망 검증.
6. 실제 플레이 화면의 다수 NPC 렌더링 및 로그 개선.

### Phase D — 통합 및 검증

1. 기존 테스트 전체 회귀 검증.
2. 신규 Actor 및 다수 NPC 테스트.
3. 절차 생성 맵 초기화 및 재현성 확인.
4. Godot 파싱 및 가능하다면 헤드리스 테스트.
5. 최종 diff 확인.
6. 문서 갱신.
7. 의도한 변경만 커밋 및 작업 브랜치 푸시.

각 Phase에서는 가급적 독립적으로 확인할 수 있는 상태를 유지하라.

구현 도중 문제가 발견되면 이전 단계의 구조를 불필요하게 다시 작성하기보다 해당 문제를 해결하는 최소한의 변경을 우선 검토하라.

## 18. 최종 중요 지침

이번 작업의 성공 기준은 Actor 관련 클래스가 존재하는지가 아니다.

다음 상태를 실제로 달성해야 한다.

**플레이어와 모든 NPC가 동일한 Actor 구조를 사용하며, 개체별 신체·능력치·HP·위치·행동 시간·AI 상태를 독립적으로 관리하고, 기존 공통 Action 및 전투 규칙을 통해 행동할 수 있어야 한다.**

새로운 쥐 한 마리를 추가하기 위해 TimeCostGame에 새로운 위치 변수, HP 변수, 행동 처리 분기문을 계속 추가해야 한다면 이번 구조 개편은 성공한 것이 아니다.

새로운 종족과 NPC를 추가할 때 기본 정의와 행동 정책을 제공하는 것만으로 기존 시스템을 재사용할 수 있는 방향을 목표로 하라.

그러나 아직 존재하지 않는 기능을 가정하여 불필요한 시스템을 대량으로 구현하지 마라.

현재의 게임 프로토타입에 필요한 최소한의 공통 구조를 구현하고, 확장성은 명확한 데이터 소유권과 책임 분리를 통해 확보하라.

**최종적으로 플레이어 1명과 쥐 3마리가 실제 게임 화면에서 독립적으로 이동·공격·후퇴·사망하는 상황을 검증하고, 기존 M011~M018의 주요 규칙이 유지되는 상태로 작업 브랜치를 완성하라.**

작업 시작 전 코드와 문서를 확인하고, 명백한 충돌이나 작업 환경상의 문제가 없는 한 추가 승인 요청 없이 구현·자동 검증·문서화·작업 브랜치 커밋 및 푸시까지 진행하라.

`main` 병합은 사용자 확인 이후 별도로 진행한다.
